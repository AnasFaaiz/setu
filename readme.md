# Setu

**Setu** (सेतु — "bridge") is a multilingual, AI-powered platform that aggregates citizen development requests — via voice, text, and messaging channels — and surfaces infrastructure priority hotspots for policymakers. Built for **Code for Communities 2 (Build with AI)**, a hackathon by hack2skill and Google Developer Groups, where problem statements are submitted directly by sitting Members of Parliament.

Setu is designed as a **Digital Public Good (DPG)**: an open, interoperable ingestion layer that any channel — a WhatsApp bot, an IVR system, a web form — can plug into, rather than a single closed application.

## The problem

Governments across India struggle to consolidate citizen feedback and align it with national infrastructure priorities. Development requests live in fragmented systems, leading to misaligned public spending, unaddressed infrastructure gaps, and no reliable way to measure the impact of digital public infrastructure initiatives.

## What Setu does

1. **Ingests** citizen feedback (text today; voice via Cloud Speech-to-Text is architected for) in any Indian language, through an open API endpoint.
2. **Understands** each submission using Gemini, extracting structured fields — topic, district, urgency — while explicitly refusing to guess when information isn't present (see [Design decisions](#design-decisions)).
3. **Fuses** aggregated feedback with real government datasets (population, infrastructure indicators) by district.
4. **Surfaces** ranked, explainable priority scores that policymakers can act on.

## Architecture

```
[Citizen input: text/voice/WhatsApp-style]
        │
        ▼
   [Ingest API] ──writes──► [feedback table, Postgres] (status: received)
        │                         (durable record BEFORE queueing)
        ▼ (returns immediately)

[RQ worker] ──dequeues ID, looks up row──►
        ├─ Gemini 3.8 Flash: structured extraction
        │   (topic / district / urgency, constrained JSON schema)
        └─ writes back → status: processed / failed (with retries)

[Fusion job] ──batch, periodic──►
        joins feedback + district_indicators (population, infra index)
        → computes explainable priority_score per district
        → writes → hotspot_scores

[API layer] ──serves──► hotspot_scores → dashboard / any consuming system
```

### Why this shape

- **Write-then-enqueue, not enqueue-then-write.** Every submission is durably stored in Postgres *before* it's queued for processing. If the queue or a worker fails, no citizen submission is silently lost — it just waits, visibly, in a known state.
- **UUID identity, generated by the API, not the database.** This decouples request identity from any single system, which is what makes the API safe to call from unpredictable, diverse clients (the actual requirement for an "open" DPG-style endpoint) without risking duplicate processing.
- **The queue carries an ID, not a payload.** Postgres is the single source of truth; the queue is just a signal to go process a specific row. This keeps queue messages small and makes reprocessing (e.g., after improving the extraction prompt) trivial — just re-enqueue existing IDs.
- **Retries with backoff, not silent failure.** External AI APIs fail transiently (rate limits, momentary overload). Jobs are retried with increasing delays rather than treated as permanently failed on the first hiccup.

## Design decisions

**District, not constituency, as the geographic unit.** Public datasets (Census, infrastructure indices) are published by district; political constituencies don't align cleanly with district boundaries and would require a separate, fragile mapping layer. District is used as the stored, joinable unit; constituency-level rollup is a natural extension once a district→constituency mapping is layered in.

**Extraction is constrained, not trusted blindly.** The Gemini extraction step uses a locked schema (fixed enum values for topic/urgency) and is explicitly instructed to return `null` for district when location isn't clearly stated, rather than inferring a plausible-sounding guess. This was verified directly: ambiguous inputs with no stated location consistently return `null`, not a fabricated place name.

**Explainable scoring over black-box ranking.** Hotspot priority is computed via a transparent formula (complaint volume, normalized by population, weighted by existing infrastructure gaps) rather than an opaque AI-generated ranking — so a policymaker can see *why* a district was flagged, not just trust an output.

## Tech stack

| Layer | Choice |
|---|---|
| API | FastAPI |
| Queue | Redis + RQ |
| Database | PostgreSQL, schema managed via Alembic migrations |
| AI/NLP | Gemini 3.8 Flash (Google AI Studio, free tier) |
| Voice (planned) | Google Cloud Speech-to-Text, Translation API |
| Public data | data.gov.in, Census, NITI Aayog district data |

## Honest scope notes

This is a solo, one-month hackathon build. It is architected to scale horizontally (stateless API, queue-decoupled workers — more load is handled by running more of each, not by redesigning the system), but has not been load-tested at production scale. Postgres today is sufficient for hackathon-scale data; read replicas and district-based partitioning are the natural next step beyond this scope, not something pretended to be solved here.

## Running locally

```bash
docker compose up -d          # Redis + Postgres
alembic upgrade head          # apply schema

# three separate terminals:
uvicorn api.main:app --reload --port 8000
python -m worker.run
```

Submit feedback:
```bash
curl -X POST http://localhost:8000/submit-feedback \
  -H "Content-Type: application/json" \
  -d '{"raw_input": "Sadak bahut kharab hai, Lucknow mein", "source_channel": "text"}'
```

Check status:
```bash
curl http://localhost:8000/status/<id>
```
