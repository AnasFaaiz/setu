# Setu

**Setu** (सेतु — "bridge") is a multilingual, AI-powered platform that aggregates citizen development requests — via voice, text, and messaging channels — and surfaces infrastructure priority hotspots for policymakers. Built for **Code for Communities 2 (Build with AI)**, a hackathon by hack2skill and Google Developer Groups, where problem statements are submitted directly by sitting Members of Parliament.

Setu is designed as a **Digital Public Good (DPG)**: an open, interoperable ingestion layer that any channel — a WhatsApp bot, an IVR system, a web form — can plug into, rather than a single closed application.

## The problem

Governments across India struggle to consolidate citizen feedback and align it with national infrastructure priorities. Development requests live in fragmented systems, leading to misaligned public spending, unaddressed infrastructure gaps, and no reliable way to measure the impact of digital public infrastructure initiatives.

## What Setu does

1. **Ingests** citizen feedback (text today; voice via Cloud Speech-to-Text is architected for, not yet built) in any Indian language, through an open API endpoint.
2. **Understands** each submission using Gemini, extracting structured fields — topic, district, urgency — while explicitly refusing to guess when information isn't present (see [Design decisions](#design-decisions)).
3. **Fuses** aggregated feedback with real government census data (population, infrastructure indicators) by district.
4. **Surfaces** ranked, explainable priority scores through an API and a dashboard, so policymakers can see not just *which* district ranks highest but *why*.

## Architecture

```
[Citizen input: text/voice/WhatsApp-style]
        │
        ▼
   [Ingest API] ──writes──► [feedback table, Postgres] (status: received)
        │                         (durable record BEFORE any processing)
        ▼ (returns immediately: "logged, awaiting triage")

[Collector] ──polls Postgres for received rows──►
        Flushes a batch when 10 are waiting, or 30s have passed with at
        least one waiting, whichever comes first.
        ├─ Sends the whole batch to Gemini in ONE call (topic/district/
        │   urgency for every complaint, matched back by ID)
        ├─ Validates the response: every ID must come back, topic/urgency
        │   must be from a fixed list, district must match a real district
        │   or be null — never a guess
        ├─ Failures retry up to 3 times, then move to needs_review
        └─ Recovery sweeper resets rows stuck mid-batch (e.g. a crash)
            back to received, based on when they were actually claimed

[Fusion job] ──run manually/periodically──►
        Groups processed feedback by district, joins with
        district_indicators (Census population, infra-access index)
        → priority_score, log-weighted so neither a tiny district's high
          per-capita rate nor a huge district's raw volume can dominate
          alone
        → writes hotspot_scores, with the full score breakdown stored
          alongside the number

[API] ──serves──► GET /hotspots (ranked list), GET /hotspots/{district}
       (score breakdown + the actual complaints behind it) → dashboard
```

### Why this shape

- **Write-then-process, not process-on-request.** Every submission is durably stored in Postgres *before* anything happens to it. If a batch fails, the data waits safely in a known state — nothing is silently lost.
- **Micro-batching instead of one API call per complaint.** Gemini's actual free-tier limit turned out to be 5 requests/minute, not the 1,500/day figure commonly cited. Batching 10 complaints into a single call turns that into roughly 50 complaints/minute of effective throughput.
- **UUID identity, generated by the API, not the database.** This decouples request identity from any single system — the actual requirement for an "open" DPG-style endpoint that unpredictable, diverse clients can call safely.
- **A validation harness sits between Gemini and the database.** Gemini's output is never trusted directly. Every batch response is checked for ID integrity, enum compliance, and district legitimacy before anything is written.
- **A daily call budget and a recovery sweeper**, since a system depending on an external AI API needs to survive both quota exhaustion and mid-batch crashes without silently corrupting or losing data.

## Design decisions

**District, not constituency, as the geographic unit.** Public datasets (Census, infrastructure indices) are published by district; political constituencies don't align cleanly with district boundaries. District is used as the stored, joinable unit; constituency-level rollup is a natural extension once a district→constituency mapping is layered in.

**Extraction is constrained, not trusted blindly.** Gemini's output uses a locked schema (fixed enum values for topic/urgency) and is explicitly instructed to return `null` for district when location isn't clearly stated, rather than inferring a plausible-sounding guess. Verified directly: ambiguous inputs with no stated location consistently return `null`, not a fabricated place name, and a genuine misclassification we caught in testing (a streetlight complaint tagged as "electricity" instead of "roads") was fixed by adding explicit disambiguation rules to the prompt.

**Census 2011 as an honest baseline, not a hidden gap.** India's most recent complete census is still 2011; the 2021 census has not been conducted. Rather than pretend this is current, population figures are scaled by a sourced national growth multiplier (~22%, 2011→2026, per UN World Population Prospects), stated explicitly as a national-average approximation, not a district-specific one.

**Explainable, log-weighted scoring over a raw or black-box formula.** An early version of the scoring formula let a small-population district with a handful of complaints outrank a large district with nearly 3x the complaint count, purely from the per-capita math. Both the complaint-rate term and the complaint-count term are log-compressed so that neither a tiny district's extreme rate nor a large district's raw volume can dominate the ranking alone — verified by hand against real output before and after the fix.

## Extraction accuracy, informally verified

A full statistically-sampled evaluation set was out of scope given the timeline, but 10 manually-labeled test cases — chosen to cover a known disambiguation edge case (streetlights vs. electricity), multi-word Indian district names, mixed Hindi/English input, and all five topic categories — were checked against real Gemini output. All 10 were correct on topic, district, and urgency. This is a small, partly hand-picked sample, not a rigorous accuracy benchmark; a proper evaluation set is listed under future work.

## Tech stack

| Layer | Choice |
|---|---|
| API | FastAPI |
| Processing | A polling collector (Postgres-backed, no message queue) |
| Database | PostgreSQL, schema managed via Alembic migrations |
| AI/NLP | Gemini 3.8 Flash (Google AI Studio, free tier), batched extraction |
| Voice (planned, not built) | Google Cloud Speech-to-Text, Translation API |
| Public data | Census 2011 district-level data (population, infrastructure-access indicators) |

## Running locally

```bash
docker compose up -d       # postgres, api, collector
alembic upgrade head       # apply schema (if not already applied)
```

Submit feedback:
```bash
curl -X POST http://localhost:8000/submit-feedback \
  -H "Content-Type: application/json" \
  -d '{"raw_input": "Sadak bahut kharab hai, Lucknow mein", "source_channel": "text"}'
```

Check status:
```bash
curl http://localhost:8000/status/<id>
```

View ranked districts:
```bash
curl http://localhost:8000/hotspots?limit=10
```

Run the fusion job after enough feedback has been processed:
```bash
python -m scripts.run_fusion
```

Open `dashboard.html` directly in a browser (points at `http://localhost:8000`) for the visual ranked view.

Set `EXTRACTOR=fake` in `.env` to run the full pipeline against a keyword-based stand-in extractor with no Gemini calls, useful for testing without spending API quota.
